\begin{abstract}
\noindent xbnh-gpu is a CUDA implementation of XBeach (trunk revision 6167) in its non-hydrostatic
(phase-resolving) mode, \code{wavemodel = nonh}. Version 2 covers every option that XBeach accepts in this
mode: one-layer and reduced two-layer flow on 1D and 2D grids of any XBeach type, all boundary types,
spectral wave boundaries, tide, wind, sources, vegetation, groundwater, ships, sediment transport and
morphology including the gravel formulations of XBeach-G, and Fortran and netCDF output. It reads XBeach
input decks unchanged and writes the same output files. On 96 feature decks, one per option, 1D runs agree
with Fortran XBeach to round-off and 2D runs to the tolerance of the iterative pressure solver; with both
solvers converged to $10^{-11}$, 2D water levels agree to $10^{-13}$. On a rip-channel beach of 0.16 to 8.7
million cells, one RTX~2000 Ada laptop GPU ran 2.0 to 3.3 times (double precision) and 3.9 to 7.5 times
(single precision) faster than XBeach with MPI on a 24-core workstation. This guide explains how to install the code without
administrator rights, build it for any recent NVIDIA GPU, run existing XBeach decks, and verify the
results against a reference XBeach build that the repository also sets up.
\end{abstract}

\section{What the code does}

XBeach in non-hydrostatic mode (\code{wavemodel = nonh}) resolves individual waves with a depth-averaged
momentum equation plus a vertical momentum equation and a non-hydrostatic pressure. The pressure is found
from a Poisson equation at every time step. These equations are local stencil operations on a structured
grid, which suit GPUs well: the cost is set by memory bandwidth, and a GPU has several times the bandwidth
of a CPU socket.

xbnh-gpu follows the XBeach Fortran source routine by routine, each routine becoming one or more CUDA
kernels:
\begin{itemize}
\item input, grid and initial state (\code{params.F90}, \code{spaceparams.F90}, \code{initialize.F90});
\item wet and dry cells and the time step (\code{wetcells.F90}, \code{timestep.F90});
\item boundary conditions, tide, wind, discharges and rainfall (\code{boundaryconditions.F90},
      \code{compute\_tide\_zs0.F90}, \code{readwind.F90}, \code{discharge.F90}, \code{rainfall.F90});
\item spectral wave boundaries (\code{waveparamsnew.F90}, \code{spectral\_wave\_bc\_module.F90}), with the
      phase-resolved sums and bound long waves on the GPU;
\item momentum, viscosity and friction (\code{flow\_timestep.F90}, \code{bedroughness.F90});
\item the non-hydrostatic predictor, breaking and pressure correction (\code{nonh.F90}), one-layer and
      reduced two-layer;
\item second-order advection (\code{flow\_secondorder.F90});
\item vegetation, groundwater, ships and drifters (\code{vegetation.F90}, \code{groundwater.F90},
      \code{ship.F90}, \code{drifters.F90});
\item sediment transport, bed update and avalanching (\code{sed\_transport.F90}, \code{morphevolution.F90},
      \code{bedroughness.F90}, \code{interp.F90});
\item output (\code{ncoutput.F90}, \code{postprocess.F90}, \code{varianceupdate.F90}).
\end{itemize}
Where the Fortran depends on its sequential loop order, the GPU code reproduces the same result. This
covers the neighbour checks of the breaking switch, loop variables that XBeach reuses from earlier loops,
in-place sweeps such as avalanching (one GPU thread per grid row or column, in XBeach order), and
single-precision constants in comparisons. Section~\ref{sec:numerics} lists the XBeach behaviours that are
reproduced on purpose.

There are two intentional differences.
\begin{enumerate}
\item \textbf{Pressure solver.} XBeach uses SIP, an incomplete-LU sweep that is sequential by
construction. xbnh-gpu solves the same five-diagonal system with Jacobi-preconditioned BiCGStab to a
relative residual of $10^{-3}$ (key \code{gpu\_solver\_acc}). In 2D the agreement with XBeach is set by the
two solver tolerances: with both tightened to $10^{-11}$ (\code{solver\_acc}, \code{gpu\_solver\_acc})
the codes agree to $10^{-13}$. 1D grids use a direct tridiagonal solve (parallel cyclic reduction), as
exact as the Fortran Thomas solve, and the same BiCGStab replaces SIP for the 2D groundwater head.
\item \textbf{Cyclic laterals.} XBeach supports \code{cyclic = 1} only under MPI, where the halo rows
1--2 and $n_y$--$n_y+1$ are copied from the opposite side of the domain (period $n_y-3$ rows). xbnh-gpu
keeps the whole domain in one block, makes the same halo copies after every update of a prognostic field,
and solves the pressure equation with periodic coupling. XBeach MPI does not exchange the velocities
between the pressure correction and the continuity equation (section~\ref{sec:numerics}); xbnh-gpu does.
\end{enumerate}

\section{Requirements}

\begin{itemize}
\item An NVIDIA GPU with compute capability 6.0 or newer: Pascal (P100, GTX 10xx) and later, including
      V100, T4, RTX 20xx/30xx/40xx, RTX Ada, A100 and H100. Check yours with \code{nvidia-smi
      --query-gpu=name,compute\_cap --format=csv}.
\item The NVIDIA driver, version 525.60 or newer (CUDA 12). On Windows, use WSL2 with the normal Windows
      NVIDIA driver; nothing GPU-related is installed inside WSL.
\item Linux x86-64, or Windows 10/11 with WSL2 (Ubuntu). Installing WSL itself may need administrator
      rights once; everything after that runs in user space.
\item About 3\,GB of disk for the build environment, and 2\,GB more for the optional reference XBeach.
\item GPU memory: about 0.8\,kB per grid cell in double precision and about half of that in single precision. An
      8.7-million-cell grid used 6.8\,GB in double precision.
\end{itemize}
No administrator rights are needed. The CUDA compiler, a compatible host C++ compiler, Python, and for
the reference model gfortran and Open MPI, all come from conda-forge through micromamba. They are
installed in the user's home directory.

\section{Installation}

\subsection{Automatic}
\begin{lstlisting}[language=bash]
git clone <repository URL> xbnh-gpu
cd xbnh-gpu
./install.sh                  # GPU code only
./install.sh --with-xbeach    # GPU code and the reference Fortran XBeach (10-20 min more)
source env.sh                 # in every new shell
bash tests/run_tests.sh
\end{lstlisting}
\code{install.sh} does the following.
\begin{enumerate}
\item It checks that \code{nvidia-smi} works and prints the GPU, its compute capability and the driver.
\item It installs micromamba in \code{\textasciitilde/.local/bin} if it is not already on the PATH.
      Environments go to \code{\$MAMBA\_ROOT\_PREFIX}, which defaults to \code{\textasciitilde/micromamba}.
\item It creates the environment \code{xbnh-gpu} from \code{environment.yml}: CUDA 12.6 \code{nvcc}, GCC
      13, make, Python 3.11 with NumPy, pandas and Matplotlib.
\item It builds \code{bin/xbnh\_gpu} (double precision) and \code{bin/xbnh\_gpu\_sp} (single precision)
      for the GPU in the machine (\code{ARCH=native}).
\item With \code{--with-xbeach}, it also creates \code{xbnh-xbeach} (gfortran 13, Open MPI, autotools,
      Subversion) and runs \code{xbeach/build\_xbeach.sh} (section~\ref{sec:xbeach}).
\item It writes \code{env.sh}, which activates the environment, puts \code{bin/} on the PATH, and sets
      \code{XBEACH\_SERIAL} and \code{XBEACH\_MPI} to the reference executables.
\end{enumerate}

\subsection{Manual}
With a CUDA toolkit (12.x) already available, for example on a cluster:

\section{Running a model}

xbnh-gpu runs in the folder that holds \code{params.txt}, like XBeach:
\begin{lstlisting}[language=bash]
cd my_deck
xbnh_gpu         # double precision
xbnh_gpu_sp      # single precision
\end{lstlisting}
\textbf{Use a separate folder from any XBeach run of the same deck.} The output files have XBeach names
and are overwritten. Linking the large input files avoids copies:
\begin{lstlisting}[language=bash]
mkdir run_gpu && cd run_gpu && cp ../xbeach_run/params.txt .
for f in z.grd nhbcflist.bcf nh_series00001.bcf water_elev.dat wind.txt hotstart_*; do
  ln -s ../xbeach_run/$f .; done
xbnh_gpu > stdout.txt
\end{lstlisting}

\subsection{Chaining segments}\label{sec:chain}
Long storms are usually run as a chain of shorter segments, each started from the state at the end of the
previous one. With \code{writehotstart = 1} the GPU code writes the nine files that \code{hotstart = 1}
reads (\code{hotstart\_zs, zb, uu, vv, wb, ws, breaking, umean, vmean} plus a six-digit number) every
\code{tinth} seconds, numbered from 1, in the same ASCII format as XBeach, so the files are interchangeable
between the two codes. A 900\,s segment written at its end is restarted with:
\begin{lstlisting}[language=bash]
mkdir seg2 && cd seg2
cp ../seg1/hotstart_*000001.dat .        # copy, do not link: seg2 writes files of the same names
cp ../deck_seg2/params.txt ../deck_seg2/water_elev.dat ../deck_seg2/wind.txt .
python $XBNH/tools/set_params.py params.txt hotstart=1 hotstartfileno=1 writehotstart=1 tinth=900 tstop=900
xbnh_gpu_sp > stdout.txt
\end{lstlisting}
Copy the hotstart files rather than linking them: a run that writes hotstart files of the same name would
write through the links into the previous segment. Time restarts from zero in every segment, as in XBeach,
so the tide, wind and boundary files of each segment start at its own $t = 0$.

\textbf{Spectral wave boundaries.} Since version 2 the GPU code synthesises the boundary series from the
spectra itself (\code{wbctype = parametric, jonstable, swan, vardens}) and writes \code{nhbcflist.bcf} and
the \code{nh\_series} files as XBeach does, so a later segment can reuse them with \code{wbctype = reuse}.
The sums over wave components, which take one to two hours on one CPU core for an offshore boundary of
several thousand rows and a 900\,s segment, run on the GPU. With \code{random = 0} the series are those of XBeach.

\subsection{Output}
Output follows \code{outputformat}, as in XBeach.
\begin{itemize}
\item \code{netcdf}: \code{xboutput.nc} with the dimensions, variables and attributes that XBeach writes
      (global, point, mean and drifter output, \code{\_parameters}), \code{remdryoutput} and
      \code{outputprecision}. Build with netCDF (the default when \code{nc-config} is found).
\item \code{fortran}: for each variable listed under \code{nglobalvar}, one file \code{<var>.dat}, one
      float64 record of $(n_x+1)(n_y+1)$ values (times the number of layers or fractions) per output time,
      with $i$ (cross-shore) varying fastest; integer variables as int32. Read it in Python with
      \code{np.fromfile('zs.dat','<f8').reshape(-1, ny+1, nx+1)}. \code{dims.dat}, \code{xy.dat},
      \code{<var>\_mean.dat} (and \code{\_var}, \code{\_min}, \code{\_max}) and \code{drifterNNN.dat} as in
      XBeach.
\item Point output for each point under \code{npoints}: \code{<name>.dat}, one record per output time of
      \code{[t, var1, var2, ...]} in float64. Points snap to the nearest cell centre, and runup gauges
      follow the waterline, as in XBeach. Output times come from \code{tintg}, \code{tintp},
      \code{tintm} or the lists \code{tsglobal}, \code{tspoints}, \code{tsmean}.
\item \code{xbgpu\_log.txt}: precision, number of steps, wall time, solver time and iterations, and cost per
      cell and step. Progress goes to standard output every 2000 steps.
\end{itemize}

\subsection{Single or double precision}
Single precision is about 2.2 times faster and uses about half the memory. In the hydrodynamic tests it
gave the same statistics as double precision; bed changes differ more (section~\ref{sec:valid}). Consumer GPUs are much slower in double precision than in
single; data-centre GPUs (A100, H100) are not.

\section{Reference XBeach and tests}\label{sec:xbeach}

\code{xbeach/build\_xbeach.sh} downloads XBeach trunk r6167 from the Deltares Subversion server
(anonymous access) and applies two small patches (\code{xbeach/patch\_xbeach.py}). It then builds
\code{xbeach/dist\_serial/bin/xbeach} and \code{xbeach/dist\_mpi/bin/xbeach} (Open MPI), with Fortran
output only. The two patches are:
\begin{enumerate}
\item \textbf{Hotstart velocities} (\code{initialize.F90}). Trunk reads \code{uu, vv} from the hotstart
      files and then sets them to zero in \code{flow\_init}, so every restart starts from rest. The patch
      keeps them.
\item \textbf{Point output} (\code{postprocess.F90}). A missing comma in a log-message format makes runs
      with output points stop at start-up with ``Missing comma between descriptors''. This happens always
      in the serial build and intermittently under MPI. Only the message format changes.
\end{enumerate}
\code{cyclic = 1} needs the MPI build with at least two ranks: \code{mpirun -np 4 \$XBEACH\_MPI}.

\subsection{Feature suite}\label{sec:suite}
\code{tests/run\_features.sh} builds one small deck per XBeach option (96 decks, listed in
\code{tests/features/suite.txt} and generated by \code{examples/features/make\_case.py}), runs them on the
GPU and checks the global output:
\begin{lstlisting}[language=bash]
bash tests/run_features.sh                  # GPU only, against stored XBeach statistics, about 5 min
bash tests/run_features.sh --xbeach -j 8    # also runs every deck in Fortran XBeach, 8 at a time
bash tests/run_features.sh sed2d gw_nh2d    # selected decks
\end{lstlisting}
The base deck is a barred beach 520\,m long at $\Delta x = 2$\,m with 120\,s of irregular waves
($H_{m0} = 1$\,m, $T_p = 8$\,s); 2D decks have 61 alongshore rows. With \code{--xbeach} the GPU output is
compared with the XBeach output field by field over $t \geq 40$\,s: relative RMS differences of $H_s$
(\code{Hs\_rel}), of the mean current (\code{current\_rel}), of the final bed (\code{bed\_rel}) and of
the sediment concentration (\code{cc\_rel}), and the RMS difference of the instantaneous water level
(\code{zs\_rms\_m}). Every other output file (extra global variables, point and runup-gauge files, mean
files, drifters, per-ship forces) is compared as well, by its largest difference relative to its largest
value (\code{files\_rel}). The limits are $10^{-6}$ for 1D decks, which agree with XBeach to round-off, and
$2 \times 10^{-3}$ ($H_s$) and $10^{-2}$ (current, bed, concentration) for 2D decks, whose agreement is
set by the pressure-solver tolerance; \code{files\_rel} has a 2D limit of 0.1, because a maximum over
all cells and times picks up cells at the waterline that are wet in one code and dry in the other. Without \code{--xbeach} the deck statistics (mean $H_s$, RMS mean
current, mean water level, RMS bed change, mean concentration) are compared with the XBeach values in
\code{tests/features/reference.json}, with the same limits.

\subsection{Quick tests}
\code{tests/run\_tests.sh} runs two small decks on the GPU in both precisions:
\begin{itemize}
\item a rip-channel beach (39\,k cells, 120\,s);
\item the cyclic-feature deck (40\,k cells, 100\,s; cyclic laterals, \code{abs\_2d}, vector boundary,
      tide and wind files, point output);
\item a hotstart round trip on the cyclic-feature deck: a 40\,s run writes a hotstart, a second run
      restarts from it, and the restarted water level and velocities must match to $10^{-6}$;
\item a per-cell Manning map: a uniform \code{bedfricfile} of 0.02 must reproduce \code{bedfriccoef = 0.02}
      to round-off ($10^{-9}$).
\end{itemize}
When the reference XBeach exists, the same decks run in Fortran XBeach and the agreement is checked
against thresholds. Otherwise the GPU statistics are checked against values stored in
\code{tests/reference.json}. The thresholds are several times the differences that XBeach itself shows
between rank counts.

\section{Numerical notes}\label{sec:numerics}

\subsection{XBeach behaviours that are reproduced}
Verification against the Fortran code exposed behaviours of XBeach r6167 that change results. xbnh-gpu
reproduces them, so that an existing deck gives the XBeach answer, except where the behaviour is a crash or
reads undefined memory.
\begin{center}\small
\begin{tabularx}{\textwidth}{lX}
\toprule
Area & XBeach r6167 behaviour \\
\midrule
\code{ts\_nonh} boundary & The first call of the boundary routine opens \code{boun\_U.bcf} and then advances it, so the first step interpolates between records. \\
Cell-centre $v_e$ & Lags one flow step (computed before the face velocity is updated); used by output and the canopy model. \\
1D wind & With \code{ny = 0} the x-directed wind also enters the y-component of the stress, so the stress is $\sqrt{2}$ too large. \\
Transport formulas & \code{mpm}, \code{wilcock\_crow}, \code{engelund\_fredsoe}, \code{wong\_parker}, \code{fl\_vb} and \code{fredsoe\_deigaard} are accepted but never called: no transport. \\
Bed load & The bed-load fluxes of the sand formulas are zero in non-hydrostatic mode. \\
\code{intrasedtr} & The suspended-load adaptation time is never set: bed load only. \\
\code{nielsen2006} & XBeach stops with a segmentation fault unless \code{streaming = 1}; xbnh-gpu runs with a warning. \\
Hotstart & Trunk XBeach sets the velocities read from the hotstart files to zero; \code{gpu\_hotstart\_keepuv = 0} reproduces this (default 1 keeps them, as the patched reference build does). \\
Placeholder defaults & Keys that a deck does not set can keep the value $-123$ and enter the computation, for example \code{tintm} in the weight of the first averaging interval. \\
2D avalanching & With a time-series boundary \code{Hrms} is not read and stays at $-123$, so the swash excursion that scales the alongshore avalanching flux is undefined; wherever an alongshore slope exceeds the critical slope the whole erodible layer moves in one step and the run fails. Set the boundary with \code{wbctype = params} or a spectrum, or avoid alongshore slopes above \code{wetslp}. \\
\code{highcomp} & The second-order components take their phases from the frequency bin above each component, a row is cleared when $k_3 h > 5$ at its first entry, and no alongshore flux is added. \\
\code{gwfastsolve} & Fills its matrix with an uninitialised index; not supported. \\
Cyclic laterals (MPI) & Velocities are not exchanged after the pressure correction (below); not reproduced. \\
\bottomrule
\end{tabularx}
\end{center}

\subsection{Other notes}
\begin{itemize}
\item \textbf{2D agreement and the solver tolerances.} Both codes stop their pressure iterations when the
residual falls below a tolerance times the norm of the right-hand side, but SIP and BiCGStab reach different
errors at the same residual. On steps with a sharp local forcing, such as the first step of a ship
pressure field, BiCGStab needs a residual two orders of magnitude smaller than SIP for the same accuracy:
on the ship test deck with waves, both codes at $10^{-11}$ differ by $10^{-6}$, and with
\code{gpu\_solver\_acc = 1e-13} they agree to $10^{-14}$.
\item \textbf{Results do not depend on the decomposition.} The GPU domain is a single block, so results
do not change with core count. XBeach MPI results do: between 2 and 4 ranks, mean currents differ by
about 3\,\% in the tests above.
\item \textbf{One cause of the XBeach drift.} XBeach MPI exchanges \code{uu, vv} after the momentum
equation, the predictor and the second-order advection. It does not exchange them after the pressure
correction, so at each subdomain seam the continuity equation uses an uncorrected halo velocity. Hotstart
files written by XBeach MPI on a field-scale deck show this: their halo rows of \code{vv} differ from the rows they copy by up to
4.6\,cm/s, while \code{zs} matches exactly.
\item \textbf{Run-to-run reproducibility.} Two runs of xbnh-gpu on the same GPU agree to about
$10^{-14}$\,m, not bit for bit, because the dot products of the solver are summed with atomic
operations.
\item \textbf{Unstable corner with Neumann laterals.} With Neumann laterals and an oblique vector
boundary, the corner where the offshore and lateral boundaries meet can become unstable in both codes.
After that, the runs separate. Use cyclic laterals for oblique seas.
\end{itemize}

\section{Troubleshooting}

\begin{description}[style=nextline]
\item[\code{nvidia-smi} not found, or ``CUDA driver version is insufficient'']
Install or update the NVIDIA driver (525.60 or newer). On WSL2, update the Windows driver; do not install
a Linux driver inside WSL.
\item[\code{nvcc fatal: Unsupported gpu architecture 'compute\_native'}]
No GPU is visible during the build (for example on a login node). Build with \code{make ARCH=sm\_XY}
from the table in section 3.
\item[``CUDA error out of memory'']
The grid is too large for the card. Use \code{xbnh\_gpu\_sp} (about half the memory) or a larger GPU.
\item[``xbnh\_gpu: ... not supported'']
The deck uses an option outside the supported list; the message names it.
\item[``time step collapsed'']
The solution became unstable and the time step went to zero; XBeach stops in the same way. Check the
deck in XBeach first.
\item[\code{micromamba create} fails or hangs (blocked conda-forge)]
Some institutional networks block or inspect traffic to conda-forge. Set the proxy first
(\code{export https\_proxy=http://proxy:port}), or skip micromamba if a CUDA toolkit (12.x, with
\code{g++} 10 or newer) is already installed: \code{make NVCC=/usr/local/cuda/bin/nvcc}, then run the
tests with any Python that has NumPy. \code{env.sh} is then not needed; put \code{bin/} on \code{PATH}
and set \code{XBNH} to the repository folder.
\item[No MPI reference XBeach (``no XBeach MPI build found'')]
The tests then compare the cyclic-feature deck with stored XBeach statistics instead, which is enough to
validate the GPU build. The MPI build needs Open MPI from \code{environment-xbeach.yml}.
\item[XBeach stops with ``Missing comma between descriptors'']
This is an unpatched XBeach with output points. Use the build from \code{xbeach/build\_xbeach.sh}.
\end{description}
